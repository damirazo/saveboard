# Работа с Saveboard

Эти инструкции действуют на весь репозиторий. Общение и проектные записи — на русском; идентификаторы кода — в существующем стиле.

## Начало задачи

1. Прочитай [текущий контекст](docs/agent/context.md) и выполни `git status --short`.
2. Перед изменениями прочитай `AGENTS.md` соответствующей части: [backend](backend/AGENTS.md), [frontend](frontend/AGENTS.md). Читай README затрагиваемого модуля.
3. Уточни результат и критерии приемки из запроса. Для многоэтапной работы используй [PLANS.md](PLANS.md); для небольшой правки достаточно плана в чате.
4. Читай архитектуру и roadmap по необходимости, не загружай всю документацию для каждой задачи.

## Контекст и решения

- Код, конфигурация и результаты выполненных проверок описывают текущее поведение. [Архитектура](docs/architecture.md) и [этапы](docs/implementation-plan.md) описывают также будущие возможности.
- При расхождении не считай документацию доказательством реализации. Зафиксируй расхождение в [вопросах](docs/agent/questions.md); исправь затронутую документацию, когда поведение выяснено.
- Не придумывай продуктовые требования. Обратимые детали выбирай самостоятельно; существенную неоднозначность уточняй, продолжая независимую работу.
- Долгосрочные решения записывай по [правилам ADR](docs/decisions/README.md). Не превращай предположение в принятое решение.

## Изменения

- Сохраняй существующие незакоммиченные изменения. Не откатывай и не включай чужую работу в коммит без необходимости и разрешения.
- Backend и frontend — отдельные pnpm workspaces с собственными lockfiles. Не объединяй их и не добавляй зависимости между частями через `workspace:`.
- Источник API-контракта — Go/Huma. После изменения DTO/маршрутов запускай из корня `pnpm api:generate`; сохраняй оба OpenAPI JSON и `schema.d.ts` вместе. Генерируемые файлы вручную не редактируй.
- Не сохраняй секреты, содержимое `.env`, токены, персональные данные или полные логи в агентских файлах.
- Для обычного перезапуска инфраструктуры сохраняй volumes. Удаление данных, production-миграции и внешняя публикация требуют явно разрешённого пользователем объёма действий.

## Проверка и передача

- Выбирай проверки по изменению: инструкции частей ниже; общая проверка — `pnpm task check`, интеграционная — `pnpm task test:integration` (Docker), браузерная — `pnpm test:e2e`.
- `node scripts/check-contract.mjs` перегенерирует файлы: учитывай это при незакоммиченном контракте. Не запускай его ради правок документации.
- Исправление поведения проверяй релевантным тестом. Для документации проверь ссылки, команды и `git diff --check`; сборка приложения без изменения кода не нужна.
- В конце сообщи результат, выполненные проверки и оставшиеся ограничения. Невыполненную проверку не называй успешной.
- Перед остановкой большой задачи обнови её план: завершённое, проверки, блокеры и конкретный следующий шаг. Обновляй текущий контекст только при значимом изменении состояния проекта; не копируй историю чата.

Навигация и примеры запросов: [разработка с Codex](docs/agent/README.md).
