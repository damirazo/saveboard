# Identity и API авторизации

Миграция `00002_identity.sql` расширяет существующую схему без удаления пользователей.
Старым пользователям назначается `user_<uuid без дефисов>`; email и пароль остаются NULL.

- `User`: UUID primary key с генерацией в PostgreSQL, обязательный username (3–64 ASCII-символа), необязательный уникальный email, encoded password hash, подтверждение email, даты создания/изменения/входа/смены пароля, статус `pending` / `active` / `disabled`, счётчик неудачных попыток и временная блокировка. Username и email уникальны без учёта регистра. Username не содержит `@`, поэтому тип идентификатора входа однозначен. При смене email приложение должно сбросить `email_verified_at`. При блокировке одновременно задаются `status = 'disabled'` и `disabled_at`; при разблокировке дата очищается.
- `OAuthIdentity`: связь пользователя с внешним аккаунтом по `(issuer, subject)`. Email провайдера не является ключом и не должен автоматически связывать аккаунты. Для OAuth2 без OIDC использовать стабильный идентификатор провайдера как issuer и его стабильный ID пользователя как subject. Поля токенов необязательны: сохранять только при необходимости, с аутентифицированным шифрованием и метаданными ключа внутри ciphertext. Конфигурация провайдеров и client secrets остаются в серверной конфигурации.
- `Session`: SHA-256 хеш случайного сессионного токена, срок действия, отзыв, последнее использование, IP и user-agent.
- `UserToken`: хеш одноразового токена подтверждения email или сброса пароля, назначение, срок действия и дата использования. Подтверждение привязано к конкретному email.
- `OAuthFlow`: хеши state, browser-cookie и OIDC nonce, зашифрованный PKCE verifier, issuer, callback URI, локальный путь возврата, срок действия и дата использования. `link_user_id` задаётся при привязке внешнего аккаунта к уже вошедшему пользователю; nonce обязателен на уровне OIDC flow, для чистого OAuth2 может отсутствовать.

Секретные поля исключены из JSON. Обновление `updated_at` для пользователей и внешних аккаунтов выполняют PostgreSQL-триггеры. API должен использовать отдельные DTO с явно выбранными публичными полями.

Миграция `00003_auth_api.sql` добавляет стабильный UUID сессии и `refresh_tokens`: SHA-256 хеш, ссылка на сессию, срок действия и дата использования. Использованные хеши сохраняются до истечения сессии для обнаружения повторного предъявления. Старое поле `sessions.token_hash` сохраняется для совместимости схемы и у новых сессий содержит хеш первого refresh-токена; API проверяет refresh только через `refresh_tokens`.

## HTTP API

- `POST /api/v1/auth/login`: JSON `{"login":"username или email","password":"..."}`. Поиск без учёта регистра. Пользователь должен иметь статус `active` и bcrypt-хеш в `password_hash`. `identity.HashPassword` создаёт хеш с cost=12; допустимая длина нового пароля — 8–72 байта. После пяти неверных попыток аккаунт блокируется на 15 минут. Число одновременных проверок паролей ограничено восемью на процесс.
- `POST /api/v1/auth/refresh`: JSON `{"refresh_token":"..."}`. Атомарно заменяет refresh-токен и выдаёт новый access JWT. При повторном использовании заменённого refresh вся связанная сессия отзывается, включая уже выданные новые токены. Параллельные refresh-запросы клиент должен объединять в один; автоматический повтор запроса с прежним refresh после потерянного ответа также потребует нового входа.
- `GET /api/v1/auth/me`: текущие `user_id` и `session_id`.
- `POST /api/v1/auth/logout`: отзывает текущую сессию.
- `POST /api/v1/auth/logout-others`: отзывает все остальные активные сессии этого пользователя. Возвращает `{"revoked":N}`; текущая сессия сохраняется при любой ротации её refresh.

Последние три метода требуют `Authorization: Bearer <access_token>`. Отсутствующий, неверный, истёкший или отозванный токен даёт 401. Cookie для доступа к API не используется. Все будущие защищённые handlers должны вызывать `AuthService.Authenticate`, который проверяет подпись/claims JWT, активность пользователя и сессии в PostgreSQL. Одна проверка подписи JWT без проверки БД не обеспечивает немедленный выход.

Вход, refresh и успешный OAuth callback возвращают JSON:

```json
{
  "access_token": "<JWT HS256>",
  "refresh_token": "<случайный одноразовый токен>",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_expires_at": "2026-11-06T12:00:00Z",
  "session_id": "<uuid>"
}
```

Access JWT живёт до 15 минут, вся сессия — 30 дней от входа без продления абсолютного срока при refresh. JWT содержит `iss`, `aud`, `sub`, `sid`, `jti`, `iat`, `exp`, `token_use=access`. При ротации ранее выданный access JWT остаётся действительным до своего истечения или отзыва сессии. Ответы имеют `Cache-Control: no-store`. Не передавайте токены в URL и не записывайте в логи; браузерный access-токен рекомендуется держать в памяти. Фронтенд входа и постоянное хранение refresh в браузере пока не реализованы.

## OAuth/OIDC

`GET /auth/login` создаёт flow на 10 минут, устанавливает HttpOnly SameSite=Lax browser-binding cookie и отвечает 302 на OIDC authorization endpoint. PKCE использует S256; verifier хранится с AES-256-GCM шифрованием и привязкой к state. `GET /auth/callback?code=...&state=...` атомарно потребляет flow, проверяет browser cookie, обменивает код сервером, проверяет подпись ID token, issuer, audience, expiry, nonce, `azp` и `at_hash` (если присутствуют). Успех возвращает JSON с локальными токенами и удаляет cookie. Токены не помещаются в redirect URL. При ошибке нужно начать новый flow; cookie истекает через 10 минут. Одновременно поддерживается одна попытка OAuth в браузере.

Первый вход создаёт пользователя с username `user_<uuid>` без локального пароля и login email; профильный email сохраняется только в `identities`. Последующие входы используют `(issuer, subject)`. Автоматического объединения по email нет. Провайдерские access/refresh-токены после проверки не сохраняются. Выход отзывает локальную сессию Saveboard; SSO-сессия Keycloak остаётся активной. Поддерживается настроенный OIDC-провайдер (в Compose — Keycloak); провайдеры чистого OAuth2 без ID token требуют отдельного адаптера.

Регистрация локальных пользователей, привязка аккаунтов, подтверждение email и восстановление пароля остаются отдельными задачами: таблицы подготовлены, публичные endpoints для них отсутствуют. Локальный пароль нельзя хранить в открытом виде; для существующего пользователя его нужно заранее задать как bcrypt-хеш. После смены/сброса пароля соответствующий сервис должен отзывать прежние сессии.

## Настройка

Обязательные переменные API: `DATABASE_URL`, `AUTH_JWT_KEY` и `AUTH_ENCRYPTION_KEY` (два разных случайных ключа по 32 байта, каждый в hex — 64 символа). `AUTH_PUBLIC_URL` — внешний origin, по умолчанию `http://localhost:8080`; HTTPS обязателен кроме loopback. Secure-флаг OAuth cookie определяется этим URL. Менять ключи нужно согласованно на всех API-инстансах: смена JWT key инвалидирует access-токены, смена encryption key — незавершённые OAuth flows.

Для OIDC: `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`; callback у провайдера должен точно совпадать с `${AUTH_PUBLIC_URL}/auth/callback`. Без `OIDC_ISSUER` локальный вход работает, OAuth возвращает 503. `OIDC_BACKCHANNEL_URL` — необязательный внутренний HTTP(S) origin для запросов API к провайдеру: меняет транспортный адрес, сохраняя публичный issuer и проверку подписи. В Compose настроен `http://keycloak:8080`; discovery выполняется лениво, без циклической зависимости старта API/nginx/Keycloak.

Из корня проекта `node scripts/init-env.mjs` добавляет отсутствующие auth-ключи в `.env`, сохраняя существующие секреты. После этого `pnpm infra:up` пересобирает сервисы и применяет миграции. При запуске API на хосте переменные из `.env` нужно экспортировать в окружение процесса; для standalone backend выполнить `pnpm migrate` перед `pnpm dev`.

Проверка: `go test ./...`, `go vet ./...`, `pnpm test:integration` (Docker, отдельные временные PostgreSQL и тестовый OIDC с подписанными ID tokens). Последовательный запуск пакетов избегает гонки инициализации Docker provider в Testcontainers на Windows. API-контракт: `pnpm api:generate` из корня.

Основа политики refresh replay: [RFC 9700, раздел 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).
