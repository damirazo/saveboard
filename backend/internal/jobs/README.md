# Фоновые задачи

River использует PostgreSQL: задачи создаются в транзакции поста. Очередь и попытки переживают перезапуск API/worker; Kafka для этой схемы не требуется.

RAG-индексация: отдельный `post.rag`, canonical text, Ollama/Qdrant, срок 30 минут и попытка 5 минут; [описание](../search/README.md). Обе разновидности используют общий слот очереди `capture`. Общий rescue 6 минут согласован с максимальным таймаутом RAG.

Для `post.capture`: три попытки всего, паузы 15 секунд и 1 минута, таймаут попытки 2 минуты, HTTP 100 секунд. Срок всей обработки, включая ожидание очереди, — 15 минут (`post_captures.deadline_at`). Смена URL/флагов или повторное сохранение после ошибки создаёт новую ревизию и срок. Поздний результат не публикуется. Пока результат не готов, API не возвращает копию или эскиз.

В Compose один worker, очередь `capture` с одним слотом; River выбирает задание при освобождении слота. Capture-сервис дополнительно допускает один браузерный запрос. Лимит River действует на процесс: при горизонтальном масштабировании нужно согласовать число worker/capture и общий бюджет ресурсов. Не добавляем замещающие слоты для неотменяемых зависших горутин: такой worker завершается и перезапускается Docker.

River восстанавливает потерянные running-задания после 6 минут (плюс интервал проверки River). Незавершённые попытки возвращаются в очередь, исчерпанные помечаются discarded. `ReconcileCaptures` при старте и каждые 30 секунд сверяет pending с очередью, сообщает о конечном сбое, отменяет просроченные/устаревшие задачи через River API и удаляет терминальные задания пакетами по 100. Running-строки не удаляются до завершения отмены. Общая страховочная очистка River — 1 час. Итог в `post_captures` и уведомление остаются.

Успех/ошибка и персональное уведомление сохраняются одной транзакцией; уникальный ключ события привязан к ревизии. Смена/удаление поста не порождает ошибочное уведомление от устаревшего задания. Потеря процесса на последней попытке обрабатывается сверкой, даже если `Work` не успел записать ошибку. При недоступной БД следующая сверка повторяется; очередь не хранится только в памяти.

Проверки: `go test -tags=integration ./internal/posts -run 'Test(LinkCaptureLifecycle|CaptureQueueRestartAndCapacity)'` из backend (Docker). Первый тест проверяет просрочку, исчерпание попыток, пропавшее задание, очистку, устаревший результат и дедупликацию; второй — реальный River, занятый слот и новый экземпляр после остановки.
