# Уведомления

`Service` читает уведомления и хранит индивидуальные отметки прочтения. Во всех запросах одинаковая область доступа: получатель отсутствует или совпадает с пользователем, `created_at` строго больше даты регистрации. HTTP дополнительно требует действующую активную сессию. Общие уведомления не отправляются задним числом новым пользователям.

Для событий сервиса вызывайте `PublishTx(ctx, tx, Event{...})` в транзакции изменения бизнес-сущности. `RecipientID=nil` означает общую рассылку; важность — `normal`, `important`, `critical`. `Key` задаёт уникальный идентификатор события для повторной доставки. `PostID` необязателен и формирует переход к посту. Публичного API создания уведомлений нет. Текст отображается как обычный текст, без HTML.

API: GET `/api/v1/notifications?page=1&size=10`, GET `/unread`, GET `/{id}`, POST `/{id}/read` относительно `/api/v1/notifications`. Прочтение идемпотентно, чужой/слишком ранний ID возвращает 404. Удаление получателя каскадно удаляет его персональные уведомления, не превращая их в общие.

Проверка: `go test -tags=integration ./internal/transport/httpapi -run TestNotificationsAPI` из backend (Docker).
